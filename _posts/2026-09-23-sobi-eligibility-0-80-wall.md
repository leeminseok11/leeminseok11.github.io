## 문제

사용자가 마이데이터를 연동하면 지원사업 공고 222건에 대해 **가능 / 확인 필요 / 불가**를 판정해야 한다. 우리가 가진 사용자 정보는 일곱 개뿐이다.

```
region  address  business_code  employee_count  open_date  annual_revenue  birth_date
```

처음 설계는 공고문에서 LLM으로 조건을 추출해 두고, 판정 때 사용자 정보와 조건을 LLM에 넣어 3분류로 답하게 하는 것이었다. 결과는 엄격 정확도(3분류 완전 일치) **0.478**.

## 0.80까지 — 범위를 좁히기

첫 도약은 모델이 아니라 **판정 범위의 재정의**였다. 체납 여부, 중복 수혜, 신용점수처럼 우리가 가진 정보로 확인할 수 없는 조건을 LLM에게 판단시키면 `unknown`과 오탈락이 쏟아진다. 실제로 오판 12건 중 9건이 이 원인이었다.

**우리가 가진 정보로 대조할 수 있는 조건만 판정한다.** 숫자·코드로 딱 떨어지면 SQL, 문장을 읽어야 하면 LLM.

| 조건 | 담당 |
|---|---|
| 시도 일치 / 전국, 소상공인 규모, 매출 상한, 업력, 마감일 | SQL |
| 시군구·읍면동, 1인 사업장, 예비창업자, 업종 일치, 대표자 연령 | LLM |
| 체납·중복 수혜·보험 가입 등 확인 불가 | 판정 안 함 → `check_items` |

후보 선별도 벡터 검색에서 SQL 정형 필터로 바꿔 포함률이 0.368 → **1.000**이 됐고, 판정 정확도는 0.478 → **0.826**.

그 다음부터가 벽이었다. 프롬프트를 여섯 번 고쳤다. 규칙을 추가하고, 절차형으로 다시 쓰고, 84줄까지 불렸다. 0.783, 0.609(하락), 0.80 언저리. 비용 때문에 공고 원문은 넣지 못하고 추출된 조건만 넣고 있었다.

## 오판을 네 종류로 나누기

숫자 하나로 보면 안 보이던 것이 보였다. 오판을 네 가지로 나눴다.

- **엄격** — 3분류 완전 일치
- **완화** — `eligible→unknown`처럼 보수적인 오판은 정답 처리
- **심각** — 가능을 불가로, 불가를 가능으로
- **위험** — 정답이 `unknown`인데 "가능/불가"로 **단정**한 수

가장 비싼 오류는 위험이다. 사장님이 서류를 떼고 신청했다가 탈락하는 경우다. 그런데 기존 설계는 프롬프트에 "대조 불가하면 unknown"이라고 쓰고 모델에게 **판정과 메타판정을 동시에** 시키고 있었다. 모델은 그 둘을 잘 구분하지 못했다.

## 설계 변경 — 모델은 2분류, unknown은 코드가

세 가지를 바꿨다.

### 1. 생성 모델 → 확률형 분류 모델

자격 판정은 자유 텍스트가 필요 없는 분류 문제다. 텍스트를 생성하지 않고 **타입 있는 질문에 확률이 붙은 결정**을 돌려주는 분류 모델(Jev)로 바꿨다. `Choice`(선택), `Noul`(참/거짓 확률). 출력 토큰 한계가 없어 10건씩 배치로 끊을 필요가 없고, JSON 파싱 실패를 방어할 코드도 사라졌다.

### 2. 공고 원문 투입

입력 비용이 낮고 출력이 무료라 **공고 원문을 통째로 넣을 수 있게 됐다.** 추출된 조건만 넣던 설계에서는 추출 누락이 그대로 오판이었다. 예를 들어 공고 117221의 지원대상은 "청년 / 생활밀접업종 / 일반소상공인 중 **택일**"인데, 추출 조건에는 셋째가 빠져 있어 택일이 AND로 보였고, 만 47세 사장님이 "청년 요건 미충족"으로 탈락했다. 원문을 넣자 살아났다.

### 3. 코드 게이트

모델은 `eligible / ineligible` **2분류만** 한다. `unknown`은 사실 질문의 답으로 코드가 덮어쓴다.

```python
if prestartup and needs_registered > FACT:                 # 사실 질문
    status = "ineligible"
elif choice == "ineligible" and confidence >= CERTAIN:     # 탈락이 우선
    status = "ineligible"
elif needs_status > FACT or needs_person > FACT:
    status = "unknown"
elif confidence < TAU:
    status = "unknown"
```

| 질문 | 묻는 것 |
|---|---|
| `needs_status` | 특정 지위·자격 보유가 필요한가 (백년소상공인 지정, 보험 가입, 신용평점 …) |
| `needs_person` | 대표자 개인 신상이 요건인가 (자녀, 출산, 성별, 장애 …) |
| `needs_registered` | 사업자등록을 마친 사업자만 신청 가능한가 |

처음엔 하나로 물었다가 네 번 실패했다. "확인할 수 없는 필수 요건이 하나라도 있는가? 결격 조항은 세지 마라" — 값이 0.74~0.86에 붙어 움직이지 않았다. 판정·메타판정·예외를 한 문장에 넣은 탓이다. **사실 하나만 묻자 0.10 ↔ 0.96으로 갈렸다.**

## 결과

| | 모델 | 입력 | 엄격 | 완화 | 심각 | 위험 |
|---|---|---|---|---|---|---|
| 배포 버전 | 생성 LLM | 조건만 | 0.797 | 0.919 | 6 | — |
| 대조군 A | 분류 모델 | 조건만 | 0.776 | 0.941 | 6 | 3 |
| **현재 C** | **분류 모델** | **조건 + 원문** | **0.972** | **1.000** | **0** | **0** |

**모델 교체 자체는 기여가 없다.** 같은 입력(조건만)에서 0.797 vs 0.776 — 사실상 동률이다. 원문 추가가 0.776 → 0.972를 만들었고, 게이트가 위험 오판을 13 → 0으로 만들었다(확정신뢰도 0.838 → 1.000).

임계값(`TAU` 0.40 / `FACT` 0.56 / `CERTAIN` 0.99)은 골든셋 85쌍을 개발/검증으로 나눠 **10회 반복** 측정으로 정했다. 0.40은 심각 오판 0을 10회 재현하는 최저값, 0.99는 0.985 아래로 내리면 심각 오판이 새는 벼랑이다. "애매한 걸 버리면 정확해지지 않나"도 확인했다 — tau를 올릴수록 확정 비율만 무너지고 맞는 답이 잘려나갔다.
