## 발견

발표를 며칠 앞두고 백업 디렉터리를 봤다. 매일 04:00에 하나씩 쌓여야 하는 덤프가 **사흘 전에 멈춰** 있었다. 그런데 Grafana도, `docker compose ps`도 전부 초록이었다. 컨테이너 10개 모두 `healthy`.

팀에 물으니 "일부러 껐다"는 설명이 나왔다. 그럴 수도 있다. 하지만 누가, 왜, 어떻게 껐는지 아무도 정확히 몰랐다. 확인하기로 했다.

## 좁히기

### 1. 안 돈 것인가, 돌았는데 실패한 것인가

가장 먼저 cron 등록을 봤다. 백업 항목은 그대로 있었다. 즉 **"안 돈 것"이 아니라 "돌았는데 실패한 것"**이다. 문제의 정의가 바뀌었다 — 껐다는 설명은 틀렸고, 뭔가가 매일 새벽 조용히 실패하고 있었다.

### 2. syslog → 백업 로그

syslog에서 cron이 04:00에 백업 스크립트를 실행한 기록을 확인했다. 백업 스크립트의 자체 로그를 열자 `pg_dump`가 **존재하지 않는 데이터베이스**에 접속하려다 실패하고 있었다. DB 이름이 비어 있었다.

### 3. .env

백업 스크립트는 서버의 `.env`에서 `POSTGRES_DB`를 읽는다. 파일을 열었다.

```
iPOSTGRES_DB=sobi
```

`POSTGRES_DB` 앞에 `i` 한 글자. 누군가 vi에서 입력 모드로 들어가며 실수로 `i`를 남긴 채 저장한 것이다. 키 이름이 `iPOSTGRES_DB`가 되면서 `POSTGRES_DB`는 **정의되지 않은 변수**가 됐고, 셸에서는 빈 문자열이 된다.

<div class="warn">원인은 환경변수 파일의 한 글자. 백업은 "DB 이름 없음"으로 매일 실패했고, 실패가 알림으로 이어지는 경로가 없어서 사흘 동안 아무도 몰랐다.</div>

## 3중 장애

여기서 끝이 아니었다. 같은 `.env`를 읽는 것이 백업 스크립트만이 아니다.

```yaml
# deploy/docker-compose.app.yml
backend:
  environment:
    SPRING_DATASOURCE_URL: jdbc:postgresql://postgres:5432/${POSTGRES_DB}
```

`${POSTGRES_DB}`가 비면 백엔드의 DB 주소는 `jdbc:postgresql://postgres:5432/`가 된다. 백엔드는 사흘째 **DB 이름 없는 주소**로 돌고 있었다. PostgreSQL JDBC는 DB 이름이 비면 사용자명과 같은 이름의 DB로 붙으려 한다 — 우연히 접속이 되는 상태라 헬스체크는 통과했지만, 다음 재시작이나 마이그레이션에서 어떻게 될지 알 수 없는 상태였다.

정리하면 세 겹이었다.

1. **백업이 멈췄다** — 매일 실패
2. **백엔드가 잘못된 DB 주소로 돌고 있었다** — 발표 당일 배포에서 터질 수 있는 상태
3. **모니터링은 전부 초록이었다** — 둘 다 "응답한다"는 이유로 정상으로 보였다

## 복구

`.env`를 고치고 백엔드만 다시 만들었다.

```bash
docker compose -f docker-compose.app.yml up -d --no-deps --force-recreate backend
```

`--no-deps`가 중요했다. 발표 직전에 DB·Redis·AI 서버까지 재시작할 이유가 없다. 환경변수를 다시 읽어야 하는 컨테이너는 backend 하나다.

## 결과

- 발표 당일 배포에서 터질 장애를 사전에 차단
- 복구 후 자동 백업 **4일 연속 성공**
- 백업 스크립트에 실패 시 Mattermost 알림을 추가 — "돌았는가"가 아니라 "성공했는가"를 알린다

<div class="tip">초록불은 '정상'이 아니라 '응답한다'일 뿐이다. 조용한 실패가 가장 위험하다. 그리고 "일부러 껐다"는 설명이 나와도, 끈 흔적이 없으면 끈 것이 아니다 — 등록부터 확인한다.</div>
